# WP-17 — Route contract

Eleven routes. The table below is generated from `apps/web/routes.py`, which is
the single declaration: paths, access policy, parameter constraints and CSRF
requirements all come from it, and `tests/unit/web/test_wp17_boundaries.py`
asserts that the registered FastAPI routes match it exactly.

| Name | Method | Path | Access | CSRF |
| --- | --- | --- | --- | --- |
| `web.home` | GET | `/` | public | – |
| `web.login` | GET | `/login` | public | – |
| `web.logout` | POST | `/logout` | public | required |
| `web.cases` | GET | `/cases` | ADMIN, DEMO_USER, EXPERT_REVIEWER | – |
| `web.case_detail` | GET | `/cases/{case_id}` | ADMIN, DEMO_USER, EXPERT_REVIEWER | – |
| `web.case_assess` | POST | `/cases/{case_id}/assess` | ADMIN, DEMO_USER, EXPERT_REVIEWER | required |
| `web.assessment` | GET | `/assessments/{assessment_id}` | ADMIN, DEMO_USER, EXPERT_REVIEWER | – |
| `web.evidence` | GET | `/evidence/{evidence_id}` | ADMIN, DEMO_USER, EXPERT_REVIEWER | – |
| `web.validation` | GET | `/validation` | ADMIN, DEMO_USER, EXPERT_REVIEWER | – |
| `web.expert_review` | GET | `/expert-reviews/{case_id}` | EXPERT_REVIEWER | – |
| `web.system` | GET | `/system` | public | – |

The machine-readable form is `schemas/wp17/web-route-surface.schema.json`,
regenerated by `python -m apps.web.artifacts`.

## Rules the table enforces at import

`apps/web/routes.py` runs `_check_table()` when the module is imported, so a
malformed table is an import error rather than a runtime surprise:

- **No duplicate name or path.** Two routes answering the same path is a
  silent shadowing bug that only shows up as "the wrong page".
- **No path under a reserved prefix.** `/api/`, `/health/` and `/openapi` belong
  to WP-16. A page that shadowed one would change what an API client receives.
- **Every POST declares `requires_csrf`.** Not "may declare" — a state-changing
  route that forgot is refused at import. The verifier itself is WP-23's, and
  until it exists the default refuses everything (see below).
- **Every parameter declares its constraint.** `case_id`, `assessment_id` and
  `evidence_id` each carry a pattern, so a path segment that is not a plausible
  identifier never reaches a handler.

## Links are built, never written

`WebRoute.url(**parameters)` is the only way a template obtains a link.
`tests/unit/web/test_wp17_boundaries.py` reads every template and fails on a
hand-written path. The consequence that matters: changing
`/evidence/{evidence_id}` changes one line, and every link that points at it
follows.

## Access policy

`AccessPolicy` is evaluated by WP-16's `require_access`, which resolves a
principal through WP-16's own security module. The interface has **no** field
for a principal and no way to construct one: it cannot establish an identity
the API would not.

Three routes are public — the home page, the login shell and the system page —
because each states what the deployment is and what it is missing, and a
deployment that could not say that until you had signed in would be harder to
audit rather than safer.

`web.expert_review` is the only route restricted to a single role, and it
renders a disabled shell in every deployment (WP-22).

## State-changing routes

Two: `web.logout` and `web.case_assess`. Both verify CSRF **before** anything
else, including before looking up whether the case exists — so an unverified
POST cannot be used to probe which identifiers are real.

In this repository both are effectively unavailable, and honestly so.
`WebProvider.csrf` defaults to `UnconfiguredCsrf`, which refuses every token
and reports `configured = False`; `WebProvider.forms_available` is then false,
and the case-detail page renders its submit control **disabled with the reason
stated** rather than offering a form that fails after an operator has filled it
in. Nothing anywhere fabricates a token to make the flow appear to work.

## Errors

A page route's failure renders an HTML error page carrying a catalogue code
and the request id — never a JSON envelope, never a stack trace, never
`str(error)`. The mapping from HTTP status to code lives in
`apps/web/factory.py` and the page itself is built by the same controlled
builder every other error uses, so no handler composes a message.

| Status | Code |
| --- | --- |
| 401 | `UNAUTHENTICATED` |
| 403 | `FORBIDDEN_ROLE` |
| 404 | `RESOURCE_NOT_FOUND` |
| 405, 422 | `REQUEST_MALFORMED` |
| 413 | `REQUEST_TOO_LARGE` |
| anything else | `INTERNAL_ERROR` |

## No OpenAPI document

`create_web_app` sets `openapi_url=None`, `docs_url=None` and `redoc_url=None`.
Pages are not an interface contract, and publishing a schema for them would
invite a client to treat rendered HTML as a stable surface. In the combined
deployment (`create_combined_app`, the `pgx-web` entry point) the served
`/openapi.json` is byte-identical to WP-16's committed artifact and contains
none of the paths above.
