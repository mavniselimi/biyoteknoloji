# WP-16 handoff

## State

The FastAPI application layer is implemented. Its framework-free half — every
decision it makes — is executed and tested wherever the suite runs. Its
framework-bound half was written and covered by static assertions on a host
with no framework; it has since been executed, and whether that has happened on
any given checkout is reported from recorded evidence rather than assumed.
Run `python -m apps.api.runtime_verification` to perform the checks and record
the result; without a current passing record the gate status reports BLOCKED.

Full suite: **4,973 passing, 32 skipped, 0 failures** (5,005 run). The 16 new
skips are the ASGI runtime tests, each skipped with a message naming
`fastapi`, `pydantic`, `starlette` and `httpx`.

## What WP-17 receives

**A closed, documented surface.** Eleven operations with stable operation ids,
declared in `apps/api/routes.py` and published in
`schemas/wp16/route-surface.schema.json`. A UI can be generated against the
OpenAPI artifact without running anything.

**Response shapes that cannot lose a governed fact.** Attention and coverage
arrive as one `status` object at every level, so a template cannot render one
without the other. Reason codes, axes, findings, evidence references and
conflict references are all present. `effect_code` and `explanation_code` are
`None` and must be rendered as absent, never as blank prose.

**The canonical clinical warning**, on every assessment response, from
`pgx/domain/claims.py`. WP-17 must display it and must not restate it.

**Three things WP-17 must not do**, each of which this layer has kept
available so that it does not have to:

1. **Do not sort a catalogue by anything but the key it arrives in.** Sorting
   by attention, by finding count or by any score is a ranking of medicines
   (SAFETY-INV-005), and it looks like a recommendation to every user.
2. **Do not summarise coverage into a badge.** "Fully covered" for a drug
   depends on which genes a case supplied; a badge computed without a case
   answers a question nobody asked.
3. **Do not re-derive anything.** Every number a page needs is in the
   response. A UI that recomputed one would be a second engine.

**Open for WP-17:** no route serves HTML and none should be added here; a UI is
a separate application that consumes this one. `Cache-Control: no-store` is set
on every response, so a UI must not rely on browser caching for assessment
data.

## What WP-23 receives

**A principal-shaped hole with exactly one filling point.**
`PrincipalResolver.resolve(credential) -> Principal` is the whole interface.
WP-23 replaces the resolver; nothing else in this layer changes.

- `Principal(actor, role, authenticated_by)` is frozen and validated. `actor`
  is bounded and printable because it is written to an append-only audit row.
- The three governed roles are `DEMO_USER`, `EXPERT_REVIEWER`, `ADMIN`, and the
  same set is independently declared in
  `pgx.application.execution_context.GOVERNED_ACTOR_ROLES`, with a test
  asserting the two agree. WP-23 adding a role must change both.
- `require_access(policy, operation_id)` enforces the route's policy. The
  matrix is in `apps/api/routes.py`; WP-23 should not need to touch it.
- `UnconfiguredAuthentication` must remain the default until WP-23 lands. It
  answers 503 and never returns a principal.
- `StaticTokenAuthentication` is development-only and is refused in production
  by `apps/api/config.py`. WP-23 should delete it, not extend it.
- The `authentication` readiness component is blocking. It becomes ready when
  `settings.auth_mode` is anything but `UNCONFIGURED`; WP-23 will want a
  stronger check — that the provider can actually reach its store.

**Things WP-23 must add, which are absent here on purpose:** rate limiting,
brute-force protection, token issuance and rotation, session management, CSRF,
and password storage. No credential is issued or accepted by this layer, so
there is nothing half-implemented to work around.

**One caution.** `authenticated_by` is a versioned mechanism label
(`"static-token/1"`). It reaches audit rows. WP-23 should mint a new label for
its mechanism rather than reusing an existing one, so that rows written before
and after the change are distinguishable.

## What WP-22 receives

Three reserved paths, each returning 501 `EXPERT_REVIEW_NOT_IMPLEMENTED` after
checking the `EXPERT_REVIEWER` role:

- `POST /api/v1/expert-reviews/{case_id}/expected`
- `POST /api/v1/expert-reviews/{case_id}/reveal`
- `POST /api/v1/expert-reviews/{case_id}/complete`

They consult no store and record nothing, so the response cannot disclose
whether a case exists and no reviewer receives a receipt for a submission that
was never recorded. WP-22 replaces the handlers; the paths, the operation ids
and the role requirement are already declared and documented.

The blinded-then-revealed ordering is the point of that workflow. A partial
implementation that revealed without having recorded an expectation would
invalidate the study, so WP-22 should land all three together or none.

## First things to do in an environment with a package index

1. `pip install -e '.[api]'` and the dev group.
2. Run the suite. The 16 ASGI tests in
   `tests/integration/api/test_asgi_runtime.py` will execute; nothing else
   should change.
3. `test_the_served_openapi_matches_the_committed_artifact` is the one that
   closes the OpenAPI gate. When it passes, regenerate
   `data/api/wp16-real-gate-status.json` — `openapi.runtime_verification` will
   still read `BLOCKED` until someone deliberately passes
   `runtime_verified=True` to `build_document`, which should be done only after
   that test has actually run and passed.
4. Point `DATABASE_URL` at a PostgreSQL instance, apply the migrations, and the
   `database` and `migrations` readiness components become checkable. They will
   still not make the instance ready: the claim boundary and the active release
   are separate gates.
