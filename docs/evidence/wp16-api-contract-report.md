# WP-16 API contract report

What was built, what was verified by executing it, and what could not be
verified here at all. The third list is as important as the first two and
is not softened anywhere in this document.

## The environment constraint, and how it stopped being permanent

WP-16 was built where FastAPI, Pydantic, Starlette, Uvicorn, HTTPX,
SQLAlchemy, Alembic and psycopg could not be installed — the package index
was unreachable, and `pip download fastapi` failed with a proxy tunnel
error. Every runtime claim in the first version of this report followed from
that, and the gate status recorded it as a set of constants.

**That was the defect.** A constant does not learn. When the framework was
later installed and the ASGI suite ran and passed, the artifact went on
saying `asgi_runtime_tests_executed: false` and
`runtime_verification: BLOCKED`, because nothing in the pipeline could
notice.

The repair is not to report execution from *dependency availability* — an
importable FastAPI is not a test that ran, and between "the packages are
here" and "the checks passed" sits every reason a check fails. Execution is
now **recorded**:

```
python -m apps.api.runtime_verification
```

composes the application, serves `/openapi.json` from it and compares that
document with the committed artifact, answers a liveness probe, and runs
`tests/integration/api/test_asgi_runtime.py`. It writes what happened to
`data/api/wp16-runtime-verification.json`, and the gate status reads that
file. Four states, and only one of them is a claim:

| State | Reported as |
| --- | --- |
| No evidence file | `BLOCKED` |
| A run where a check failed | `VERIFICATION_FAILED` |
| A passing run whose inputs have since changed | `STALE_EVIDENCE_REJECTED` |
| A passing run whose inputs still match | `VERIFIED` |

Staleness is measured against three fingerprints: the `apps/api` source, the
generator's output, and the committed artifact — each with the
`x-pgx-runtime-verification` block excluded, so recording a verification
cannot invalidate the evidence for that verification.

What remains blocked regardless of the host:

- **No PostgreSQL service has been started or reached.** No migration was
  applied and no row was written or read. `psycopg` being installed does not
  change this and is reported separately.
- No dependency lock file was written and no resolution was run.
- The claim boundary is unapproved, authentication is unimplemented, and no
  release is active. None of those is an environment problem.

**No stand-in was vendored.** There is no `fastapi/`, `pydantic/`,
`starlette/`, `uvicorn/` or `httpx/` directory in this repository, and
`TestTheSkipIsHonest` asserts it — because the one repair nobody should
make is replacing a missing framework with a look-alike and calling the
result a pass.

## What that leaves verified by execution

The API layer is split so that **every decision is in a module that runs
without a web framework**. The framework-free half imports only the standard
library and `pgx`, and `tests/unit/api/test_wp16_boundaries.py` imports every
one of its modules to prove it. That split is why the layer was fully testable
before the framework was available, and it is why the runtime checks have so
little left to establish.

`apps/api/runtime_verification.py` is the one framework-free module that
*drives* the framework, and it does so only inside function bodies — a
subprocess test imports it with the framework blocked, to prove the gate
status can still be built on a host that has none.

Verified by executing the real code, over the real WP-14 synthetic world:

- the request contract, its bounds, patterns, vocabularies and prohibitions;
- the recursive prohibited-field scan, including a `genotype` nested three
  levels down and a `vcf_path` inside a list the contract does not declare;
- the request adapter through the real WP-12 normaliser and the real WP-14
  input builder;
- one real assessment executed by the real service through the real engine,
  persisted, and read back;
- the response serialiser on both paths, asserted to produce identical
  governed facts;
- release pinning, including a pointer moved mid-flight;
- request-id isolation from every semantic hash;
- the error catalogue, the status table, the total exception mapper;
- the role matrix, the fail-closed resolver, the stub refusals;
- pagination, cursor binding and cursor refusal;
- readiness, including a probe that raises and a probe that cannot import;
- the claim scanner over every message, every envelope, every readiness
  detail, the whole OpenAPI document and a real synthetic response;
- the OpenAPI generator, its determinism and the committed artifact.

Not verified by execution, and covered by reading the source as a syntax
tree instead: the routers, the factory, the middleware, the dependency
providers and the Pydantic generation. Those hold no decisions — the tests
assert that every route they register comes from the route table, addressed
by operation id, with no hand-written path and no locally-built access
policy. **A static test is not counted as an executed ASGI test anywhere in
this report.**

## Defects found and fixed during WP-16

Recorded because each was a real hole that the tests opened, not a
stylistic change:

1. **Responses could not be validated at all.** The prohibited-field scan
   ran on every document, and the prohibited names — `attention`,
   `coverage`, `findings`, `input_hash` — are exactly what a response
   carries. Every valid response was a violation. Fixed by gating the scan
   on `direction == "request"`. The tempting repair — deleting entries from
   the prohibited list until responses passed — would have opened the
   request side one field at a time.
2. **Array item vocabularies were unenforced and undocumented.** Fields
   whose items are governed enums declared no item vocabulary, so the
   validator checked nothing and the OpenAPI document emitted
   `{"type": "enum"}` — telling a generated client that coverage reason
   codes were unconstrained strings. Fixed by adding `item_enum_values`,
   refusing an enum-item field that omits it, and routing item schemas
   through the same generator as scalars.
3. **Two observations naming one gene collapsed silently.** The list-to-
   mapping conversion let the later entry win, so a client sending `POOR`
   and `NORMAL` for one gene would have received a confident assessment of
   whichever was last. Now refused with `DUPLICATE_ITEM` at the duplicate's
   index.
4. **`details` was unbounded.** `ContractViolation` truncated its own
   issues, but every other caller could hand `error_envelope` a list of any
   length. Bounding and key-filtering moved into `error_envelope`, once.
5. **The cursor bound was too small for the cursor.** 256 characters could
   not hold the release, dataset and manifest identity a cursor must carry
   to be refusable across releases. Raised to 512 with the arithmetic
   recorded beside it.
6. **The gate status counted a README as a report.** It reported
   `real_report_count: 1` by counting `*.md` in `data/reports/`, which
   contains a README explaining why the directory is empty. Now read from
   WP-15's own gate status, which the reporting layer maintains.
7. **Declared path patterns were documented and not enforced.** Routers typed
   path parameters as bare `str`, so a malformed identifier reached the domain
   parser and came back as a **500** — for a value the contract already
   documented as unacceptable, and with the parser's message quoting the value
   it could not read. Parameters are now built from the route table by
   `apps.api.dependencies.parameter`, so the documented constraint and the
   enforced one are the same object, and `InvalidIdentifierError` maps to a
   422 as a second line of defence.
8. **The evidence adapter read key names the repository does not use.** It
   looked for `snapshot_id`, `artifact_digest` and `json_pointer`; WP-08
   emits `snapshot_manifest_hash`, `artifact_sha256` and `pointer`. Against
   the real repository every locator would have come back with four nulls.
   Found by rewriting the fixture to carry WP-08's actual keys — including
   `artifact_path` and `requested_container`, which must not be emitted and
   now demonstrably are not. The projection also gained the record-type
   mapping (identifiers and status, never its curation `rationale`).
9. **The artifact generator measured the tree mid-update.** `write_artifacts`
   built everything including the gate status and then wrote it all, so the
   gate status recorded `artifact_matches_generator: false` about a mismatch
   the same call was about to fix — and a freshly regenerated tree failed its
   own freshness test. The gate status is now built after the derived
   artifacts are on disk, and `build_gate_status` takes the root it measures,
   so it can never describe one tree while living in another.

## Test counts

Measured on the full suite, not asserted:

```
PYTHONDONTWRITEBYTECODE=1 python3 -W error::ResourceWarning \
  -m unittest discover -s tests -p 'test_*.py' -t .

Ran 5005 tests in 100.673s
OK (skipped=32)
```

Baseline before WP-16, re-measured rather than assumed: 4,687 passing,
16 skipped, 0 failures.
After WP-16: **4,973 passing, 32 skipped, 0 failures** (5,005 run).

The 16 new skips are the ASGI runtime tests, every one of them skipped with
the same precise reason naming `fastapi`, `pydantic`, `starlette` and
`httpx`. The 16 pre-existing skips are unchanged.

## Zero-real-data status

No real assessment exists in this repository, none has been created through
the API, no report has been published, and no endpoint returns a synthetic
fixture. The fixtures under `tests/fixtures/wp16/` are reachable only from
tests: routers read from the injected `ServiceProvider`, and a deployment
with no provider for a capability answers with that capability's typed
unavailability rather than with a fixture. Every fixture value is visibly
synthetic — `TEST-` prefixes, `TESTGENE`/`testdrug` entities, dates in 2099.
